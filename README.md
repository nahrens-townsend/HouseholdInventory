# HouseholdInventory

A backend system for tracking household items, rooms, and warranty expiration dates. Built with ASP.NET Core 10, Entity Framework Core, and HotChocolate GraphQL. Deployed to Azure App Service with automated CI/CD via GitHub Actions.

---

## Architecture Overview

The solution follows a three-layer architecture designed to keep domain logic isolated from infrastructure and delivery concerns.

```
HouseholdInventory/
├── src/
│   ├── Inventory.Core/           # Domain entities — no dependencies on other projects
│   ├── Inventory.Infrastructure/ # EF Core DbContext and migrations
│   └── Inventory.Api/            # ASP.NET Core controllers, GraphQL, background service
└── tests/
    └── Inventory.Api.Tests/      # Integration tests (xUnit + WebApplicationFactory)
```

**Why this structure:**

- **Core** has zero dependencies. Entities can be reasoned about without understanding persistence or HTTP.
- **Infrastructure** owns the database — schema, migrations, and `DbContext` configuration are all in one place.
- **Api** is the composition root. It wires up DI, configures middleware, and exposes both REST and GraphQL surfaces.

Controllers inject `InventoryDbContext` directly — no repository layer. This is intentional: for a system of this size, a repository abstraction adds indirection without benefit.

## Features

### REST API

Full CRUD for both resources, served via attribute-routed controllers.

| Method | Endpoint | Description |
|---|---|---|
| GET | `/rooms` | List all rooms |
| POST | `/rooms` | Create a room |
| PUT | `/rooms/{id}` | Update a room |
| DELETE | `/rooms/{id}` | Delete a room |
| GET | `/rooms/{id}/items` | List all items in a room |
| GET | `/items` | List all inventory items |
| GET | `/items/{id}` | Get a single item |
| POST | `/items` | Create an inventory item |
| PUT | `/items/{id}` | Update an inventory item |
| DELETE | `/items/{id}` | Delete an inventory item |

Swagger UI is available at `/swagger` in all environments.

### GraphQL API

Served via HotChocolate at `/graphql`. Supports automatic query projection, filtering, and sorting on all list queries.

**Queries**
- `rooms` — list with filtering, sorting, projections
- `items` — list with filtering, sorting, projections
- `roomById(id)` — single room including its items
- `itemById(id)` — single item including its room

**Mutations**
- `createRoom` / `updateRoom` / `deleteRoom`
- `createItem` / `updateItem` / `deleteItem`

The interactive Banana Cake Pop playground is available at `/graphql` during development.

### Background Service

`WarrantyReminderService` runs as an in-process `IHostedService`. On each cycle it:

1. Queries for items whose `WarrantyExpiry` falls within the next 5 days.
2. Checks whether a reminder for that item already exists within the warning window.
3. Creates a `WarrantyReminder` record if none exists.

The check interval defaults to 24 hours and is configurable via `appsettings.json`:

```json
"WarrantyReminderService": {
  "CheckIntervalInMinutes": 1440
}
```

Because `DbContext` is scoped and the service is a singleton, the service creates a DI scope per cycle using `IServiceScopeFactory`.

### Database

Three tables managed via EF Core migrations:

- **Rooms** — a named location in the house
- **InventoryItems** — an item in a room; tracks name, purchase price, purchase date, warranty expiry, and optional serial number / notes
- **WarrantyReminders** — a reminder record generated by the background service

**Relationships:**
- `Room` → `InventoryItem`: one-to-many, delete restricted (a room cannot be deleted while it contains items)
- `InventoryItem` → `WarrantyReminder`: one-to-many, delete cascade

## How to Run Locally

**Prerequisites:** .NET 10 SDK, SQL Server (local instance or Docker), `dotnet-ef` CLI tool.

### 1. Clone and build

```bash
git clone https://github.com/nahrens-townsend/HouseholdInventory.git
cd HouseholdInventory
dotnet build HouseholdInventory.slnx
```

### 2. Configure the connection string

Edit `src/Inventory.Api/appsettings.Development.json` and set the `Default` connection string to point at your local SQL Server instance:

```json
{
  "ConnectionStrings": {
    "Default": "Server=localhost;Database=HouseholdInventoryDb;Trusted_Connection=True;TrustServerCertificate=True"
  }
}
```

### 3. Apply EF migrations

```bash
dotnet ef database update \
  --project src/Inventory.Infrastructure \
  --startup-project src/Inventory.Api
```

### 4. Run the API

```bash
dotnet run --project src/Inventory.Api
```

| Interface | URL |
|---|---|
| Swagger UI | `https://localhost:{port}/swagger` |
| GraphQL Playground | `https://localhost:{port}/graphql` |

### 5. Run tests

```bash
dotnet test HouseholdInventory.slnx
```

Tests use EF Core InMemory — no database connection required.

## Azure Deployment

The application runs on Azure App Service backed by Azure SQL Database.

### Configuration

The production connection string is injected via an Azure App Service **Application Setting** named `ConnectionStrings__Default`. ASP.NET Core's configuration system maps this environment variable directly to `ConnectionStrings:Default` — no code changes needed between environments.

### GitHub Actions Pipeline

Every push to `master` triggers a four-job pipeline:

```
test → build → migrate → deploy
```

| Job | What it does |
|---|---|
| **test** | Restores dependencies and runs the full test suite |
| **build** | Compiles the solution and publishes the API artifact |
| **migrate** | Installs `dotnet-ef`, then runs `database update` against Azure SQL using a connection string stored as a GitHub Secret |
| **deploy** | Downloads the publish artifact and deploys to Azure App Service |

Deployment to Azure uses **OpenID Connect (OIDC) federated identity** — no long-lived credentials are stored. The pipeline authenticates via `azure/login@v2` using service principal credentials stored as GitHub Secrets.

Migrations are always applied before deployment, ensuring the schema is updated before the new code goes live.

## Testing

### Strategy

All tests are integration tests that exercise the full ASP.NET Core pipeline — middleware, routing, model binding, DI, and EF Core — without mocking any of those layers.

**`InventoryWebAppFactory`** extends `WebApplicationFactory<Program>` to:
- Replace the SQL Server `DbContext` registration with an EF Core InMemory provider.
- Assign each test class its own isolated database (via `Guid` DB name), preventing state bleed between test classes.
- Remove `WarrantyReminderService` from the pipeline so background timers don't interfere with deterministic tests.

### Test Coverage

| File | What it tests |
|---|---|
| `ItemsControllerTests` | REST CRUD for inventory items |
| `RoomsControllerTests` | REST CRUD for rooms and room-scoped item queries |
| `GraphQlItemsTests` | GraphQL queries and mutations for items via HTTP POST to `/graphql` |
| `GraphQlRoomsTests` | GraphQL queries and mutations for rooms via HTTP POST to `/graphql` |
| `WarrantyReminderServiceTests` | `ProcessWarrantyRemindersAsync` logic — expiry detection, deduplication, and reminder creation |

The `WarrantyReminderService` is tested by calling `ProcessWarrantyRemindersAsync` directly with a controlled `today` date, decoupling the test from real-time scheduling.

The test suite runs automatically on every push as the first job in the CI pipeline — the build and deployment jobs will not run if tests fail.

## Design Decisions

### REST and GraphQL coexist

REST is the default interface: well-understood, easy to browse via Swagger, and simple to consume from any client. GraphQL addresses the cases where REST's fixed response shapes become limiting — particularly for querying items by room, fetching items with specific warranty windows, or any query where a consumer wants to select only a subset of fields. Having both surfaces available means neither imposes unnecessary constraints on the other.

### Background service runs in-process

`WarrantyReminderService` runs inside the API process rather than as a separate worker service. For a system at this scale, the operational overhead of a separate deployment (its own App Service plan, its own CI pipeline, its own configuration surface) outweighs the isolation benefit. The service uses `IServiceScopeFactory` to safely resolve the scoped `DbContext` from a singleton, which is the standard ASP.NET Core pattern for this case.

### EF Core is used directly in controllers — no repository layer

Introducing a repository abstraction over EF Core would mean writing interfaces and classes that mirror what `DbContext` already provides. At this scale, that adds boilerplate with no payoff: it doesn't simplify testing (EF InMemory handles that), doesn't simplify the query model, and doesn't improve separation of concerns in any meaningful way. The rule here is: add abstraction when complexity demands it, not by default.

### Layered architecture over flat structure

Keeping `Core`, `Infrastructure`, and `Api` as separate projects enforces dependency direction at compile time. `Core` cannot accidentally reference EF Core. `Infrastructure` cannot accidentally reference ASP.NET Core. Violations are build errors, not code review comments. As the system grows — additional workers, a scheduler, a notification service — each can reference `Core` and `Infrastructure` without pulling in the HTTP layer.
